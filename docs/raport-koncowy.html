Wniosek: logowanie SSH jest dobrze zabezpieczone, ale host nie ma własnej zapory, a agenci AI działają na koncie z uprawnieniami roota (sudo bez hasła, grupy docker i lxd) bez reguł ograniczających w .claude/settings.json. 1Zadanie i zakres

Treść zadania: „uruchom dedykowany skill healthcheck w OpenClaw w celu przeprowadzenia audytu zabezpieczeń serwera SSH, konfiguracji zapory sieciowej (firewall) oraz weryfikacji uprawnień w pliku .claude/settings.json”.

Serwer SSH

Efektywna konfiguracja sshd -T, pliki sshd_config.d, klucze, ochrona przed brute-force.

Zapora sieciowa

ufw, iptables, nftables i usługi nasłuchujące na interfejsach publicznych.

.claude/settings.json

Reguły deny/ask/allow, tryb domyślny, hooki, sekrety w env, prawa pliku.

Poza zakresem. Zadanie obejmuje audyt, więc poprawki nie zostały wprowadzone. Plan naprawczy jest w sekcji 8 jako rekomendacje. Audyt odbywał się wyłącznie w trybie odczytu, a narzędzie po każdym przebiegu sprawdza, czy stan maszyny się nie zmienił.

3Narzędzie openclaw-audit i skill /audyt-hosta

Narzędzie jest reużywalne: wszystkie dane maszyny pochodzą z jednego pliku konfiguracji, a cały proces (wymagania, środowisko, audyt, raport, sprzątanie) uruchamia jedno polecenie albo skill Claude Code.

Plik i wymaganiawalidacja pliku (parsowany, nie wykonywany), test SSH, tabela wymagań OK/BRAK z poleceniami naprawylaptop → maszyna
2
Środowiskoprywatny Node 24 LTS i OpenClaw w ~/.openclaw-audit, oba z kontrolą SHA-256; bez sudo, bez skryptów npmmaszyna
3
AudytA: 26 kontroli deterministycznych. B: skill healthcheck (agent --local)maszyna
4
Raportkontrola, czy konfiguracja się nie zmieniła; pobranie wyników i złożenie REPORT.mdlaptop
5
Sprzątanieusunięcie ~/.openclaw-audit (1,2 GB) i porównanie katalogu domowego ze zdjęciem sprzed instalacjimaszyna
Zabezpieczenia narzędzia
  • Klucz API jest czytany z pliku i przesyłany przez stdin SSH, więc nie trafia do argumentów ani logów
  • Dowody wymagające uprawnień zbiera skrypt, a agent dostaje zakaz używania sudo i wprowadzania zmian
  • Wartości env w settings.json są maskowane, zanim trafią do modelu
  • Po audycie porównanie sshd -T, ufw i SHA-256 settings.json ze stanem sprzed audytu
  • Gateway OpenClaw nie jest uruchamiany, więc nie ma żadnego nowego portu
  • Cały ślad w jednym katalogu: systemowy Node, ~/.openclaw i ~/.npm nietknięte. Po sprzątaniu raport potwierdza: „brak nowych ścieżek”
  • Braki w wymaganiach są zgłaszane z poleceniem naprawy, nigdy instalowane samodzielnie
Jakość i powtarzalność
  • 20 testów parsera konfiguracji i diagnozy połączenia, w tym próby wstrzyknięcia polecenia
  • Kontrola śladów przetestowana na podrzuconym pliku: wykryty i zgłoszony
  • Skaner sekretów jako hook pre-commit i krok CI
  • CI w GitHub Actions: składnia, ShellCheck, testy, skan
  • Instalacja jest idempotentna: ponowne uruchomienie pomija wykonane już kroki
  • Oba tryby dostępu do modelu przetestowane: Claude CLI na maszynie i klucz API (klucz nie wyciekł do wyników, logów, historii, /tmp ani dziennika)

Uruchomienie

Serwer SSH

7Weryfikacja wyników agenta

Wynik agenta potraktowałem jako drugą opinię, a nie rozstrzygnięcie. Kluczowe twierdzenia sprawdziłem ręcznie poleceniami tylko do odczytu i porównałem dwa niezależne przebiegi.

Potwierdzone ręcznie
  • allowagentforwarding yes, permitopen any w sshd -T
  • ~/.claude 775, settings.json 664
  • nginx :80 i :18881 odpowiadają HTTP 200
  • 50-cloud-init.conf ma prawa 600 root, czyli prawdziwa luka odczytu bez sudo
  • Kontrola po audycie: sshd, ufw i settings.json bez zmian (oba przebiegi)
Problemy z wynikiem agenta
  • Pominięta grupa lxd: druga, obok docker, droga do uprawnień roota. Była w dowodach, a agent przeoczył ją w obu przebiegach
  • Złamanie zakazu: agent uruchomił sudo -n true, mimo zakazu sudo. Sam to zgłosił w sekcji „Luki”. Polecenie było nieszkodliwe, ale prompt nie jest bramką
  • Niedeterminizm: 14 ustaleń w 1. przebiegu, 17 w 2. Wnioski główne są spójne, ale oceny ważności i nowe ustalenia się różnią
  • W 2. przebiegu agent podał w raporcie fragment publicznego IP operatora (usunięty z tej wersji)

9Wnioski i ograniczenia

Wnioski
  • Skill healthcheck dobrze interpretuje kontekst: koryguje ważność i dokłada nieoczywiste ustalenia. Słabiej sprawdza się jako kompletna lista kontrolna
  • Najlepszy wynik daje połączenie powtarzalnych reguł (bramka) i agenta (analiza) z ręczną weryfikacją kluczowych twierdzeń
  • Największe ryzyko hosta nie leży w SSH, tylko w połączeniu agentów AI, roota i braku reguł w settings.json. To dokładnie trzeci punkt zadania
  • Ocena rozszerzenia przed instalacją (checklista) wykazała lukę skilla względem zadania, zanim cokolwiek uruchomiłem
Ograniczenia
  • Zakaz zmian dla agenta jest instrukcją, a nie granicą. Kontrola po audycie tylko wykrywa zmiany. Twardą granicę dałoby konto bez sudo
  • NSG Azure jest niewidoczny z hosta, więc waga ustaleń o zaporze jest warunkowa
  • Wynik agenta jest niedeterministyczny. Do porównań w czasie służy część A
  • Raport opisuje przebieg w trybie Claude CLI; przebieg z kluczem API dał zgodne wnioski, ale wynik agenta różni się między przebiegami
